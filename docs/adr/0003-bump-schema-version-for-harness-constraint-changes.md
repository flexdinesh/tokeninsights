# Bump schema version for harness constraint changes

Status: Updated 2026-09-09. Automatic compatibility recovery supersedes the original manual-reset requirement.

When adding a new persisted harness ID, TokenInsights bumps SQLite `user_version`: expanding a harness `CHECK` constraint is logically additive, but existing databases physically reject the new value. Structure changes still require a schema compatibility break rather than a row-by-row migration path.

Normal sync/normalize and TUI/web startup now automatically rebuild recognized older schema/data. Schema V8 adds singleton lifecycle state with current data generation 1, rebuild-pending status, and `rebuild_source_key`: a normalized source-configuration hash, NULL when ready and nonempty while pending. Breaking token semantics or identity changes bump data generation; structure changes bump schema version. Release version numbers do not determine compatibility.

Recovery holds a database-scoped writer lock, transactionally recreates application tables in the existing SQLite file with pending state and source hash, then reimports and normalizes all configured local harnesses. It never unlinks live SQLite/WAL files. Failed recovery retains partial work and resumes without resetting again only when normalized source configuration matches. Default keys include effective OpenCode/Pi/Codex/Claude Code roots; custom all-harness keys use the canonical absolute root. Mismatches reject before data writes. Repeat the original `--source-dir`, `--db-path`, and source environment settings; full paths are never persisted or recovered from the hash. Analytics reads validate lifecycle inside their read transaction and reject unfinished recovery. Compatible/fresh databases keep current data. Unknown, corrupt, or newer files are rejected without automatic deletion.

Targeted default-source recovery expands to all default harnesses; all-harness custom roots remain bounded; single-harness custom-root recovery defers without mutation. Missing harnesses remain normal skips. `--no-sync` stays read-only, `--dry-run` previews without writes, and explicit `reset-all` remains available. Rebuild can reconstruct only retained local sources. `reset-canonical` requires compatible, fully recovered data and cannot repair incompatible raw usage.
